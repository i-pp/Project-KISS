## 1. 概要

Project-KISS
は、単なるソフトウェア製品や事業計画ではなく、設計思想・原則・マニフェストを中心に据えたプロジェクトである。複雑さを人間や個々のアプリケーションへ押し付けず、システム側が複雑さを引き受け、観測・検証・再生成・最適化を循環させることを目指す。

全体は、最上位のプロジェクト、そのサブプロジェクト、統合システム、および統合システムを構成するコンポーネントとして整理する。

- **Project-KISS**：ACE／PAUL／GENE／PETERなどの各コンポーネントとAceISを開発する、最上位のプロジェクト。
- **Project-ACE**：Project-KISSのサブプロジェクト。各コンポーネントを組み合わせ、AceISを設計・実装・検証する。
- **AceIS**：ACE／PAUL／GENE／PETERなどを包含する次世代の統合システム。従来の「OS」という呼称に限定せず、**IS（Integrated / Intelligence / Individual System）**として位置づける。

概念上の関係は次のとおり。

```text
Project-KISS
├── ACE / PAUL / GENE / PETER などの各コンポーネント開発
└── Project-ACE（Project-KISSのサブプロジェクト）
    └── AceIS（ACE / PAUL / GENE / PETER などを包含する統合IS）
        ├── ACE：推論・検証・自己改善を担う知的コンポーネント
        ├── PAUL：Program Analysis & Unification Layer
        ├── GENE：Generative Execution & Native Engine
        ├── PETER：Portable Execution & Translation Environment
        ├── AceIS Core：統合システムとしての全体制御・判断
        ├── A-Nexus：共通抽象化・資源仲介・リアルタイム制御基盤
        ├── Abiss (ABISS)：最小限のハードウェア境界 / HAL
        └── Runtime / ABI / API / Compiler / Linker / Toolchain integration
```

**用語の使い分け**

- **Project-ACE**はサブプロジェクトの名称であり、個別コンポーネントの**ACE**とは別の概念である。ACE単体の開発だけを指すものではなく、AceIS全体の統合・設計・実装・検証を扱う。Project-ACEの名称展開 **Autonomous Cognitive Evolution** はプロジェクト名の構想上の展開として扱う。
- **ACE**はAceISを構成する知的コンポーネントを指し、推論、検証、改善候補の導出などを担う。
- **AceIS Core**はAceIS全体の統合制御・判断を担うシステム上の中核を指す。ACEの知的機能そのものと同義ではない。両者の詳細なAPI、実行配置、責務境界は今後定義する。
- **AceIS**は個別コンポーネント名でもProject-ACEの別名でもなく、各コンポーネントを包含する統合システムの名称である。
- **IS**はIntegrated、Intelligence、Individualの各概念を含むSystemを表す。AceIS自体を単に「OS」と呼ぶことは避ける。ただし、技術分類や既存OSとの比較など、一般概念としての「OS」は必要に応じて使用する。

この図は概念上の境界を示す。コンポーネントとサブプロジェクトの成果物の対応、プロセス分割、実行形式、通信プロトコル、各要素の配置などは今後の設計事項であり、まだ固定されていない。

## 2. Project-KISS：設計思想

### 2.1 中核原則

**複雑なものを複雑なまま人間に押し付けない。**

KISS（Keep It Simple,
Stupid）は、単にコード行数や機能を減らす標語ではない。利用者、開発者、運用者が本来意識しなくてよい複雑さを、適切な層が吸収するという設計原則である。

-   利用者に不要な内部事情を露出させない。
-   既存資産との共存を妨げず、段階的な移行を可能にする。
-   システムの内部は高度でも、利用方法や理解に必要な概念は可能な限り単純にする。
-   便利さをブラックボックス化と混同しない。システムの動作は観測でき、検証可能であること。
-   失敗を隠さず、再現・診断・修正につなげられるようにする。
-   特定の個人が常時介入し続けないと成立しない運用構造を避ける。

### 2.2 Individual（個人を中心としたシステム）

AceIS
は、組織の都合や管理者の都合を中心に置くのではなく、個人が使い、制御し、長期的に育てられるシステムを志向する。

ここでいう Individual
は、単に「個人向け製品」という意味に限らない。利用者ごとの環境・機器・ワークロードに適応しながら、利用者の自由と制御可能性を保つという考え方を含む。

### 2.3 自由と共存

-   新しいシステムへの移行を強制しない。
-   旧製品・既存ソフトウェアとの共存を可能にする。
-   既存資産を捨てることを進歩の条件にしない。
-   オープンな開発と公開を基本とし、特定企業による独占的な秘匿をプロジェクトの価値の中心に置かない。
-   利用者が自らの環境を理解し、制御し、変更できる余地を残す。

### 2.4 人間の新しい体験

性能指標だけでなく、コンピュータを使う人間の体験そのものを設計対象とする。OS、コンパイラ、Runtime、AIを別々の製品として積み重ねるだけではなく、全体を一つのシステムとして設計することで、従来は利用者が手作業で行っていた調整や保守をシステム側へ移す。

### 2.5 作る側と使う側、両方のワクワク

**エンジニアのワクワクと、エンドユーザーのワクワクを両立することを、AceISの必須設計原則とする。** 便利さや性能だけではなく、作る過程・使う過程の双方に発見、理解、手応え、自由があることを重視する。

- **エンジニア:** 起動・内部動作を観察できる、自分の変更を試せる、測定結果を比較できる、システムの仕組みを理解しながら改善できる。
- **エンドユーザー:** 面倒な設定や保守に振り回されず、自分の目的に集中できる。システムが環境に適応し、改善の恩恵を実感できる。
- **循環:** 開発者の発見や改善が検証されて共有され、各環境で適合性を確かめて利用者の体験を改善し、その結果が次の開発の知見になる。
- **非目標:** AIが無断で機能を増やすことや、数値ベンチマークだけを上げることを「ワクワク」と同一視しない。利用者の制御、理解可能性、安全性、リアルタイム制約を維持する。

最初のユーザーはエンジニアである可能性が高い。したがって、最初のHelloWorldから、動かす・観察する・実験する・改善するという体験を提供する。最小実装は機能数だけで定義せず、エンジニアが「もっと触りたい」と思えることも評価する。

### 2.6 マニフェストの性格

Project-KISS
の対外文書は、事業計画や収益計画よりも、コンセプト、設計思想、自由、Individual、SIMD
Native、Minimum AI RTOS、RTOS with Gaming
Specs、ロボット・航空宇宙を含む適用領域、人間の新しい体験を前面に出す。

音楽・文化的な参照は、ブランドの雰囲気や文章の端々に使うことがある。ただし、既存バンド等の商標・ロゴ・意匠を混同させる表現は避け、独自の識別性を保つ。

## 3. Project-ACE：技術体系

### 3.1 目的

Project-ACEはProject-KISSのサブプロジェクトであり、ACE／PAUL／GENE／PETERなどのコンポーネントを統合し、AceISを設計・実装・検証する。

名称展開と、Project-ACE・ACEコンポーネントの区別は、第1節「用語の使い分け」を参照する。

### 3.2 フィードバック・ループ

基本的な循環は次のとおり。

1.  **観測:**
    実行時の挙動、性能、障害、構成、ハードウェア特性を記録する。
2.  **解析:** 生ログや実行情報をもとに、原因・傾向・改善候補を抽出する。
3.  **仮説・変更案:** 改善候補を具体的な変更として定義する。
4.  **生成・ビルド:** コンパイラや生成系で変更を実装・ビルドする。
5.  **検証:** テスト、カバレッジ、互換性、性能、回帰の観点で検証する。
6.  **適用判断:** 検証結果とリスクに基づいて適用可否を決める。
7.  **再観測:** 適用後の実測値を記録し、仮説と結果を比較する。

AIが変更を提案・生成できることと、無条件で本番環境へ適用できることは別である。変更の権限、検証要件、ロールバック方式、最終承認条件はコンポーネントのリスクに応じて定義する。

## 4. コンポーネントの役割分担

ACE／PAUL／GENE／PETERは、AceISを構成する機能上のコンポーネントである。役割名は、単一の巨大なエージェントへすべての仕事を集約せず、機能責任を分離するための概念モデルである。実装方式、使用モデル、プロセス分割は固定されていない。

### 4.1 ACE（コンポーネント）--- 推論・検証・自己改善

-   問題・制約・設計意図を推論する。
-   変更案を評価し、検証結果から改善候補を導く。
-   生成物の正しさを独立した観点から検査する。
-   観測データと過去の結果を用い、改善サイクルを支援する。

### 4.2 PAUL --- Program Analysis & Unification Layer

-   ソースコード、依存関係、ビルド設定、API/ABIの関係を解析する。
-   異なるコンポーネント間の整合性を把握する。
-   解析結果を統合し、変更の影響範囲を明らかにする。
-   コンパイラ・リンカを中心とするプログラム解析機能を担う。

### 4.3 GENE --- Generative Execution & Native Engine

-   コード生成、実行、ネイティブ化に関わる機能を担う。
-   生成した変更をビルド・実行・測定できる仕組みと連携する。
-   実行結果を検証工程へ返す。

### 4.4 PETER --- Portable Execution & Translation Environment

-   移植、変換、互換性の確保を担う。
-   異なるCPU、ABI、実行環境の差異を扱う。
-   既存ソフトウェア資産と新しいネイティブ環境をつなぐ。

### 4.5 分離の意図

解析、生成、検証、移植を概念的に分離することで、責任範囲、失敗箇所、レビュー観点を明確にする。AIモデルが異なる場合や、将来モデルを置き換える場合にも、各機能の契約を維持できる構造を目指す。

各役割を必ず別プロセス・別モデルにするという決定ではない。独立性が必要な箇所、共通化すべき箇所、通信契約は実装段階で決定する。

## 5. AceIS：統合IS／Runtime構想

### 5.1 位置づけ

AceISは、ACE／PAUL／GENE／PETERなどのコンポーネントを包含し、Runtime、ABI/API、コンパイラとの連携を含む統合システムである。**「ACE Individual System」という展開ではなく、IS（Integrated / Intelligence / Individual System）の概念で位置づける。**「OS」は既存の技術分類として必要に応じて使用するが、AceIS自体の呼称には用いない。

ACEコンポーネントとAceIS Coreの区別は、第1節「用語の使い分け」を参照する。

### 5.2 システム基盤の方向性

-   最小構成のAI対応RTOS（Minimum AI RTOS）を出発点の一つとする。
-   将来的には一般用途OS、RTOS、ゲーミング、ロボット、航空宇宙などへの適用を視野に入れる。
-   カーネルはハードウェア抽象化・保護・資源管理などの基盤を担い、AIコアや高位の知的機能をユーザーランド側に配置する方向を検討する。
-   初期段階では既存の仕組みとの互換性を入口として利用し、長期的には独自API/ABIを持つネイティブ環境を目指す。
-   既存のamd64向けLinux／Windowsアプリ・ライブラリとのバイナリ互換は、初期段階の互換レイヤー(5.7)として、本体とは別パッケージで提供する。**[方針]**
-   Android等その他の互換・共存は検討対象だが、初期段階の要件ではない。

### 5.3 POSIXから独自API/ABIへ

POSIX互換は、既存ソフトウェアや開発ツールを活用するための初期の入口として扱う。POSIXを最終設計の絶対条件とはせず、AceISの目的に合わせてAPI/ABIを設計する。

移行では、互換レイヤーとネイティブ環境の境界を明確にし、互換性のための複雑さがカーネル全体に波及しない構造を目指す。独自API/ABIの具体的な仕様、バージョニング、互換性ポリシーは未確定。

### 5.4 AceISの基本レイヤー構造

基本構造は **Hardware → Abiss → A-Nexus → AceIS Core** とする。ここでの矢印は主な依存・制御経路を示し、全処理が必ず全レイヤーを通過するという意味ではない。

#### Abiss (ABISS) — HAL / ハードウェア境界

Abissはハードウェアに最も近いソフトウェア層であり、可能な限り小さく保つ。ハードウェア固有の初期化、低レベル制御、上位層に公開する最小限の機能を担当する。名称展開は構想上の仮称であり、語源や正式な略語展開の精緻化は後回しにする。

#### A-Nexus — 共通抽象化・資源仲介層

A-Nexusは、共通の抽象化、仮想化、資源仲介、通常のハードウェア操作、リアルタイム制御を担う。AceIS Coreは基本的にA-Nexusの機能を利用する。一方で、A-Nexusをあらゆる処理の必須経路にはせず、低レベル機能やハードウェア固有機能を必要とする開発者には、明示的なAbiss直接アクセス経路を用意する。

直接アクセスは、MMIO、DMA、割り込み制御などへの無制限な権限を意味しない。権限、排他制御、メモリ保護、安全条件、リアルタイム制約は維持する。A-Nexusの抽象化を迂回できることと、保護機構を迂回できることを混同しない。

#### AceIS Core — 自律思考・自己成長の中核

AceIS Coreは、システムの観測、推論、改善候補の選定、検証結果の評価、全体方針の判断を担う。AceISはシステム全体の名称であり、AceIS Coreはその中の自律思考・自己成長の中核を指す。

### 5.5 起動順序とレイヤーの責務

基本的な立ち上げ順序は **Abiss → A-Nexus → AceIS Core** とする。Abissが最低限のハードウェア初期化と実行基盤を用意し、A-Nexusが共通資源管理・制御機能を初期化した後、AceIS Coreが稼働する。ブートROM、初期ブートローダー、検証・復旧機構などの詳細は別途定義する。

リアルタイム性はレイヤー名や直接操作だけで保証されるものではない。割り込み経路、スケジューリング、ロック、メモリ割り当て、キャッシュ・メモリ帯域干渉、優先度逆転、最悪実行時間などを含めて保証対象と測定条件を定義する。A-Nexusはリアルタイム性を支える中心的な制御基盤とするが、時間保証は実装と検証によって成立させる。

### 5.6 自律的な構成最適化と自己改善

AceISがハードウェア構成、ドライバ、実行負荷、性能データを把握し、構成やビルド成果物を自律的に改善する構想がある。クラウド由来の知見を利用する可能性もあるが、機密データの送信を前提にしない。ローカル処理、データ持ち出し制御、更新の検証、ロールバックは設計上の重要事項となる。

「自動で変更できる」ことを「検証なしに変更してよい」ことと同義にしない。安全性・リアルタイム性・セキュリティに関わる不変条件は、AIの判断だけでは変更できないよう、権限・検証経路を技術的に分離する。

### 5.7 互換レイヤー

-   **目的:** AceISの初期段階として、既存資産(amd64向けのWindows／Linuxアプリ・ライブラリ)をバイナリ互換で使えるようにする。**[方針]**
-   **構成:** 動的ローダーが既存バイナリを解釈・変換し、libposix、liblinux、libwin32のような互換ライブラリを通して動かす構成を想定する。名称と分割は仮である。**[方針]**
-   **提供形態:** 本体とは切り離し、利用者が必要なときに別途インストールするランタイムとして提供する。最終的に削除する前提で、最初から分離して用意する。**[方針]**
-   **配置:** 原則としてユーザーランドに閉じる。**[方針]**
-   **本体との依存方向:** 本体から互換レイヤーへの依存を作らない。互換レイヤーは本体の公開API/ABIのみを使う。削除時に本体のビルドが壊れないための規則とする。**[提案]**
-   **削除条件:** 「いつ、どの基準で削除するか」をADRで定義する(例: ネイティブAPIで主要アプリが動く、利用実績が一定以下)。**[提案]**
-   **段階案:** 難易度が段階ごとに大きく異なるため、次の順に進める。**[提案]**
    1.  静的リンクのLinux ELF(syscallの変換が中心)
    2.  動的リンクのLinux ELF(glibc／muslのABI互換が必要)
    3.  Windows PE(kernel32／ntdll相当の挙動が必要。規模が大きい)
-   **実装上の注意(著作権・ライセンス):** Wine、ReactOS、glibc等の他実装のソースを参照しながら書くと、コード混入や派生物の問題が生じうる。公開仕様、ドキュメント、挙動観察から実装する(クリーンルーム的な手順)。**[提案]**
-   **初期ターゲットとの関係:** 初期ターゲットがamd64であれば、既存のx86_64バイナリを命令変換なしで動かせるため、互換レイヤーの検証が容易になる。aarch64やRISC-Vを最初に選ぶと、バイナリ変換(PETERの役割)が最初から必要になる。初期ターゲット選定の判断材料とする。**[提案]**

### 5.8 実行モードとアプリケーション用サンドボックス

-   サンドボックス化は、実効速度が担保できる場合に採用する。速度を犠牲にする隔離は採らない。**[方針]**
-   速度のためにデバイスとの直通経路(DMAのようなもの)が必要な場合は、モードを用意して扱う。**[方針]**
-   既定は隔離モードとし、利用者が明示的に選べる性能モード(直通を許可)を用意する。どちらを選んだかはログに残す。**[提案]**
-   直通経路の保護にはIOMMU(Intel VT-d、ARM SMMU等)の利用を検討する。既存の実例としてVFIO、DPDK／SPDK、io_uring等がある。**[提案]**
-   互換レイヤーが同一プロセス内でsyscallを変換する方式であれば、ptraceやseccompによる横取りよりもオーバーヘッドが小さいと見込まれる。要測定。**[提案]**
-   互換アプリ側のセキュリティ(元アプリの脆弱性)は利用者の責任とし、気にする利用者はNativeアプリをビルドして使う。ただしAceIS本体のセキュリティを放棄するものではない。**[方針]**
-   互換アプリが侵害されても、本体やNativeアプリへ波及しないよう、本体との境界(権限、アドレス空間、ファイル範囲)は保証する。**[提案]**

### 5.9 自己改善用サンドボックス

AceISは、通常処理のために常時重いサンドボックスを動かすのではなく、改善候補を安全に検証するための専用サンドボックスを備える。ACEが異常や改善機会を検知した場合、または共有サーバーから候補パッチを受け取った場合などに利用する。

- **候補の準備:** 変更候補の生成・コンパイル・リンクなど、時間のかかる処理は可能な限り事前に実施し、検証時点では実行可能な候補を用意しておく。
- **検証機会:** 空き時間を推定できる場合はその時間を利用する。推定できない場合は、対象処理の期限と干渉条件を把握したうえで安全な検証タイミングを選ぶ。
- **短時間検証:** 検証対象を限定し、事前準備されたテストや局所的な不変条件の確認をマイクロ秒オーダーで実施できる設計を目指す。
- **包括検証:** 任意のカーネル変更や複雑な並行処理を、数マイクロ秒で完全に検証できるとは想定しない。広範なテスト、競合条件、長期安定性などはバックグラウンドや開発環境で別途検証する。
- **本番系との分離:** サンドボックスのCPU時間、メモリ、キャッシュ、メモリ帯域、I/O、割り込み等が本番処理の期限を破らないようにする。単に処理を中断可能にするだけでは不十分である。
- **採否:** 検証結果、性能、機能的正当性、安全制約、リアルタイム制約をもとに採否を決める。集約ベンチマークの改善は、明示された不変条件違反を正当化しない。
- **失敗時:** 候補を破棄し、現行実装を維持する。適用後も結果を観測し、必要に応じて安全な復旧経路で戻せるようにする。

「マイクロ秒オーダーで検証できる設計」は重要な目標だが、すべての変更の完全検証を保証するという意味ではない。短時間で検証可能な変更単位・条件・テストを設計し、それ以外は検証段階を分ける。

## 6. SIMD Native とハードウェア差異の吸収

### 6.1 基本方針

SIMD Native
は、SIMDを特別な最適化オプションとして利用者が毎回意識するのではなく、システムやコンパイラがCPUの能力に応じて活用できる状態を目指す構想である。

-   CPUごとの命令セット・機能差をシステム側で吸収する。
-   コンパイラがターゲットCPUや機能セットに応じたコードを生成する。
-   必要に応じて実行環境が適切な実装を選択できるようにする。
-   可搬性とネイティブ性能の両立を目指す。

### 6.2 未確定事項

SIMDを常に有効にする具体的な意味、ベースラインISA、機能検出方式、複数実装のディスパッチ方式、浮動小数点の再現性、バイナリ配布形式は未確定。性能を優先する場合でも、移植性や結果の正しさを損なわない仕様が必要である。

## 7. RTOS・リアルタイム設計の関心事項

設計者の組込みOS／RTOS経験を背景に、次の問題を重要な設計検討事項とする。

-   CPU pinningを前提にしない運用・スケジューリングの可能性。
-   IRQ処理やリアルタイム処理のためのコア分離・資源管理。
-   デッドロック、優先度逆転、割り込み遅延、ジッタの観測と診断。
-   実行状態を長期にわたって追跡できる常時トレース。
-   ログの保持・検索・解析を前提にした設計。
-   TSN/gPTP等の時刻同期・決定性ネットワークへの関心。
-   RTOSのリアルタイム性と、ゲーミング用途で求められる性能・応答性の両立。
-   AIの判断や大規模ビルドをリアルタイム経路から切り離し、事前準備済み候補の短時間検証のみを制御されたタイミングで実施する。
-   ナノ秒単位を一律の要求にせず、対象ごとに必要な時間粒度・期限・ジッタを定義する。マイクロ秒オーダーの局所検証経路を目標とするが、全変更に対する完全検証の時間保証とは区別する。

これらは設計上の重点領域であり、すべてが実装済み、あるいは確定要件という意味ではない。リアルタイム保証を主張するには、最悪実行時間、割り込み応答、スケジューリング、負荷条件、測定方法を明示する必要がある。

## 8. ログ、観測可能性、自己改善

### 8.1 Rawログを一次記録とする

AIによる要約や圧縮メモリだけを唯一の記録源にしない。一次情報としてのrawログを保持し、AIはそこから解析・索引・要約を生成する。AIが過去の記録を都合よく書き換えられない構造を重視する。

-   原本ログとAI生成の派生データを分離する。
-   タイムスタンプ、発生元、対象コンポーネント、イベント種別、相関IDなどを検討する。
-   ログの欠落、順序、時計同期、破損検出を設計対象とする。
-   保存期間、容量、プライバシー、機密情報の扱いを明確にする。
-   AIの判断・変更と、その根拠になったログを関連付ける。

### 8.2 長期トレース

長期間の連続観測（1～2か月程度の保持構想を含む）が関心事項である。ログ容量の目標やレコード幅（64/128
bit等）は検討段階であり、固定仕様ではない。記録量、イベント頻度、圧縮、リングバッファ、外部ストレージ、障害時の保全方式を測定して決める。

### 8.3 再現性と監査可能性

AIが提案した変更について、入力、関連ログ、生成物、テスト結果、承認、適用結果を追跡できることを目指す。要約だけでなく、根拠となる原本データへ戻れることが重要である。

## 9. セキュリティと脅威モデル

本節は第1版に存在しなかった新設の節であり、脅威モデルの正式化は未決事項(第17節)である。

### 9.1 基本姿勢

-   完璧な事前防御は存在しないため、侵入を完全には防げない前提(assume breach)で設計する。**[方針]**
-   不審な動きをAIが検出して隔離・解析し、対策パッチを作成して無害化を図り、レポートを共有する。検出から対策・共有までを通じた自己改善と個体間の同期は、ACEコンポーネントが担う機能の一つである。**[方針]**
-   AceISはOSSとして全てが公開されるため、標的になることを前提にする。攻撃者による解析(他のOS上での解析を含む)は防げない前提とし、秘匿に依存しない。**[方針]**
-   AIによる検出は最後の砦であり、最初の防御ではない。メモリ安全な言語の活用、最小権限、権限分離といった基本の防御を土台にして重ねる。**[提案]**

### 9.2 互換レイヤー経由の脅威

-   互換レイヤーを通して動くマルウェアには、互換レイヤーの使用権を剥奪することで対処する(使わせない、動かないようにする)。**[方針]**
-   OpenSSH等の正規アプリに脆弱性がある場合、脆弱なバージョンでも動作はする。対策は修正版を使うことである。**[方針]**
-   使用権剥奪の判断者、署名された拒否リストの運用、誤判定時に利用者が上書きできる経路は未決である。**[提案]**
-   ソースが入手できない既存バイナリへの対策は、元アプリではなく、互換レイヤーや実行環境側のポリシー(許可するsyscallの絞り込み等、いわゆる仮想パッチ)で行う。**[提案]**

### 9.3 個体の貢献度・信用度

-   貢献度・信用度の指標が付く対象は利用者ではなく、AceISの個体そのものである。どの個体の貢献度が高いかを、人間は知らなくてよい。**[方針]**
-   評価の基礎は、個体が報告するログ(利用者がこうしたらシステムがこう動いた、という記録)の価値である。そのためクラックウェアを作る利用者の個体でも、貢献度が上がる可能性がある。**[方針]**
-   貢献度・信頼性の高い個体からの情報は、早く追加確認され、全個体へ通知(pushでもpullでもよい)され、自動更新される。**[方針]**
-   偽装されたレポートに対しては、別の個体から、偽装を指摘するレポートが届く。**[方針]**
-   信頼度は確認の優先順位にだけ作用させ、確認の厳しさは下げない。信頼を長期間積んでから偽情報を流す手口に備えるためである。**[提案]**
-   レポートの価値は、独立した個体や隔離環境で再現できたかどうかで測る。**[提案]**
-   偽の個体の大量作成(Sybil攻撃)に備え、同じ出所の個体が互いに評価を押し上げられない設計にする。**[提案]**
-   数値を人間に公開しない場合でも、判断の根拠は改ざん不能な監査ログとして残し、追跡可能にする。rawログを一次記録とする原則(第8節)と整合させる。**[提案]**

### 9.4 更新とパッチ採択経路

-   更新はOTAによる完成済みイメージの配布ではなく、必要最小限の差分を取得し、AceIS側でビルド・検証したうえで取り込む方式とする。**[方針]**
-   中心となる論点は、攻撃者が作ったパッチを誤って取り込まないために、パッチがどの経路で採択されるかである。**[方針]**

採択経路の骨格案は次のとおり。**[提案]**

1.  出所を問わず、すべてのパッチを信頼できない入力として扱う。
2.  証拠(レポート、信頼度)と権限を分ける。信頼度は調査の優先順位にだけ効かせ、採択の権限は次の関門を通ったものにだけ与える。
3.  出所に依存しない関門: 脆弱性・不具合の隔離環境での再現、パッチによる解消の確認、既存テストの通過、主張範囲外の変更がないことの差分レビュー(AIと人間の双方)、サンドボックス内でのパッチ前後の挙動比較(syscall、入出力の記録)。
4.  異なる構成・ハードウェアの個体による独立した検証と、結果の一致の確認。
5.  全体への採択は、複数の鍵による閾値署名を必須とする。
6.  段階展開(一部の個体に先に配り、健全性を確認してから広げる)と、巻き戻し(A/B方式等)。
7.  再現可能ビルドとし、個体間でビルド結果のハッシュを突き合わせて、侵害されたビルド環境を検出する。
8.  個体内で完結し、巻き戻し可能な緩和策（隔離、権限の絞り込み）は、定義済みの制約内でAceISが自動適用してよい。全体に波及するパッチは、上記の全関門と署名を必須とする。
9.  採択経路そのもの(検証、署名、更新、信頼判断のコード)は、通常の採択経路とは別の、より厳しい手続き(人間の関与の必須化等)で保護する。判断する仕組みが、自分自身のルールを単独で書き換えられないようにする。
10. ビルド環境への信頼(ace-ccの自己ホスト化におけるブートストラップの検証、いわゆるtrusting trust問題)を設計課題として扱う。

その他の注意点: **[提案]**

-   AIによる監視・隔離機構自体が標的になる。監視機構は監視対象とは別の権限・別の領域に置く。
-   レポートや対策を共有・同期する経路も攻撃面である。署名と検証、出所の追跡を最初から入れる。
-   残余リスクとして、テストにもレビューにも通る巧妙なバックドア(xz utilsの事件のような手口)が残る。完全には防げないため、再現可能ビルド、挙動の差分比較、多様な検証者の組み合わせで、発見の確率を上げる。

### 9.5 プライバシーと同意

「利用者の行動に対してシステムがどう動いたか」というログを個体間で共有する構想では、何を収集するか、どこまで匿名化するか、利用者が明示的に同意しているかを決める必要がある。個人情報保護法、GDPR等の対象になりうるため、専門家の確認を要する。利用者の制御を重んじるIndividualの思想とも関わる。**[提案]**

## 10. コンパイラ／リンカと開発環境

### 10.1 専用コンパイラ ace-cc

-   Project-KISS／Project-ACEの初期実装として、専用コンパイラ ace-cc を開発する。**[方針]**
-   LLVMや既存コンパイラのコードを生成物に取り込まない。ace-ccのバックエンドとして、LLVM系ランタイムを必要としない。**[方針]**
-   gcc、clangは、ace-ccが完成するまでの間に限って使用し、完成後は使用しない。**[方針]**
-   gcc／clangは、ace-ccをビルドするためのホストコンパイラ、および出力を比較する差分テストの基準(オラクル)としてのみ使う。**[提案]**
-   ace-ccの自己ホスト化に向けて、ブートストラップの手順と検証方法を決める。**[提案]**

### 10.2 ランタイムライブラリ libace_rt

-   `-lc`、`-lgcc`のようなリンク引数を利用者に意識させないことを目標とする。**[方針]**
-   ランタイムライブラリを作る場合の名称は libace_rt とする。POSIX互換のみ検討が必要である。**[方針]**
-   libgcc／compiler-rt相当の機能(128ビット整数演算、ソフトフロート、memcpy系、スタック保護等)を自作の範囲に含め、既存ライブラリのライセンス条件に依存しない。**[提案]**

### 10.3 初期PoCの範囲

初期段階では、OS全体を一度に実装せず、ace-ccによるクロスコンパイラ／リンカ周辺の小さなPoCから始める方針がある。

-   ホスト: x86_64/amd64
-   初期ターゲット: まず1つのCPUアーキテクチャに絞る
-   対象: クロスコンパイラ、リンカ、ターゲット向けライブラリ等の基盤
-   検証: 生成コード、アセンブリ、リンク結果、テスト
-   目標: 初期テスト群を含めて1分以内を目指す
-   並列テスト: 数百件規模(約500件を目安にした構想)が検討されている

上記は初期PoCの目標・候補であり、測定済みの性能保証ではない。実際の時間はテスト内容、ホスト、キャッシュ、並列度に依存する。

### 10.4 ターゲット切替

ターゲットCPUの切替をライブラリ等で扱い、ターゲットが増えた際のビルド・テストコストを管理する構想がある。`-mcpu`、`-march`等の指定を含め、ターゲット設定を散在させずに管理することを目指す。

最初からaarch64、amd64、RISC-Vを同時に完成させるのではなく、まず単一ターゲットでビルド・テスト・生成物検証の流れを完成させ、その後に対象を増やす。

### 10.5 言語・実装上の志向

-   C/C++を中心に考える。
-   Rustも対象候補に含む。
-   Python中心の実装層を増やすことは避けたい。
-   シェルやCLIを重視し、GUI/WebUIを必須にしない。
-   QEMU、Renode、KVM等の実用的な検証環境を優先候補とし、初期から高価な仮想プラットフォームに依存しない。

言語やツールの最終選定は、初期PoCでの保守性、生成物、デバッグ可能性、実行速度を評価して確定する。

### 10.6 Ace Intermediate Representation（AIR）と責務境界

- **[方針]** 独自のターゲット非依存中間表現を **Ace Intermediate Representation（AIR、エアー）** と呼ぶ。ソース言語とターゲットISAの組合せごとにコンパイラ全体を作り直さず、AIRを境界として分離する。
- **[方針]** LLVM IRやLLVMバックエンドへの依存を前提としない。既存GCC/Clang等は初期ブートストラップ、比較検証用の外部ツールとして扱い、独自コンパイラの生成経路とは区別する。
- **[設計整理]** PAULはソース解析・意味解析・AIRへの変換を中心に、GENEはAIRからのターゲット命令選択・SIMDネイティブコード生成を中心に、PETERは異なるISA・ABI・実行環境間の移植・変換・互換性を中心に担う。これは既存の概念責務をコンパイラPoCへ具体化したものであり、モジュール境界やAPIは未確定。
- **[提案]** AIRでは演算幅、符号、整数オーバーフロー、浮動小数点、メモリアクセス、アラインメント、ベクトルlane順序などの意味を明示し、ターゲット間で結果を比較できるようにする。
- **[提案]** 最初のPoCは単一ターゲットのx86-64に限定し、定数returnなどの最小生成経路から始め、次に128-bit SIMDの加減算・論理演算などへ進む。AArch64 NEON/SVE、RISC-V等は後続段階で追加する。

### 10.7 SIMDネイティブの既定動作とターゲット指定

- **[方針]** SIMDネイティブをコード生成の基本方針とし、利用者が毎回SIMD最適化を明示的に有効化する必要のないコンパイラを目指す。ただし、SIMD化が不適切な処理まで強制する意味ではない。
- **[方針]** スカラーコード生成を明示的に選ぶオプションとして `-fforce-scalar` を設ける構想とする。正確な適用範囲、ABI、ベクトル型を含む場合の扱いは仕様化が必要。
- **[方針]** クロスコンパイルを基本設計に含める。`--target` はターゲット環境、`-march` は命令セットの指定として分離する。`-mcpu`/`-mtune` は必要に応じて後続で検討する。
- **[提案]** ホストCPUの自動検出はクロスターゲットの命令選択に混入させない。`-march=native` 等を導入する場合のみ明示的に区別する。
- **[未検証]** SIMD優先生成の性能・コードサイズ・正しさは、スカラー生成と既存コンパイラの参照結果を用いて実測する。既存Clang等との性能同等性は保証しない。

### 10.8 クラッシュ解析を先行させるデバッグ方針

**設計判断：対話型SIMD専用デバッガを初期PoCの前提条件にしない。Core DumpとAIR対応情報を先に整備し、障害解析可能な状態でコンパイラ開発を継続する。** **[方針]**

初期の最低限の解析経路は次のとおり。

1. **実行・障害記録：** テスト入力、コンパイラ・ターゲット設定、ビルド識別子、生成物、終了状態を記録する。
2. **Core Dump：** Linux/ELF上で異常終了した場合、OS設定・保存先・容量制限・アクセス権を確認したうえでCore Dumpを収集する。すべての異常で必ず取得できるとは限らない。
3. **AIR Mapping：** AIR命令・関数と生成機械語のアドレス範囲の対応を、生成コードとは別に保存する。生成物識別子と結び付け、最適化で対応が消失・複数化する場合も表現可能にする。初期PoCでは最小の対応表から始める。
4. **事後解析：** GDB等の既存ツールでPC、スタック、汎用レジスタ、取得可能なSIMD拡張レジスタ、逆アセンブルを調べ、AIR Mappingと照合する。Core Dumpに含まれるレジスタ状態はOS・CPU・保存設定に依存する。
5. **証拠保存：** Core Dump、生成バイナリ、AIR、Mapping、テスト入力、解析結果を関連付ける。Core Dumpには機密情報が含まれうるため、保存権限・保持期間・外部送信禁止を設ける。

**制約：** Core Dumpは停止時点の状態であり、過去の命令実行履歴を復元するものではない。計算結果の誤りが正常終了した場合にも通常は生成されない。したがって、差分テストと、後続の任意地点状態ダンプ・命令ステップ・SIMD lane比較を補完手段として設計する。

**段階案：** PoC-0＝Core Dump + 最小AIR Mapping + GDB解析、PoC-1＝任意地点状態ダンプ、PoC-2＝AIRと物理SIMDレジスタの対応表示・lane差分、後続＝AIR対応の対話型SIMDデバッガ。GDB Python拡張は試作候補であり、GDB forkや独自デバッガの実装を現段階で確定しない。

**完了条件（PoC-0のデバッグ経路）：** 意図的に異常終了する小さな生成プログラムを用意し、保存したCore Dumpと同一ビルドの生成物から停止PC・機械語・対応AIR位置を再現可能に確認できること。取得失敗時には原因と代替の診断記録を残すこと。

### 10.9 ローカルLLMによるコンパイラPoC開発実験

- **[方針]** 初期コンパイラPoCのコード実装はローカルLLMを主たる実行主体とし、その能力・限界を検証する実験として扱う。クラウドAIが実装を代行した成果と混同しない。
- **[提案]** Chat/dotは設計、タスク定義、検証基準、結果レビューを支援し、ローカルLLMの実装成果には入力・モデル・生成結果・テスト結果の追跡可能性を持たせる。
- **[提案]** NPU常駐オーケストレーション等の開発基盤改善は独立タスクとして管理し、コンパイラPoCを無期限に待機させる必須条件としない。利用可能な既存ローカル環境で最小実装と検証を開始できる構造を優先する。
- **[未検証]** ローカルLLMが独立してPoCを完成できるか、品質・所要時間・メモリ資源にどの程度制約されるかは実測する。

## 11. ソースコードとテストの規約

### 11.1 ファイル先頭の情報

各ソースファイルのヘッダから、少なくとも次の情報を把握できることを目指す。

-   ファイルの目的と責務
-   関係するコンポーネント、API、依存関係
-   ビルド・コンパイラコマンドや必要な設定
-   テストとの対応関係
-   必要な場合の生成元や更新手順

コメントは説明責任を果たすために書く。自明なコードを冗長に言い換えるだけのコメントは増やさず、目的・制約・非自明な理由を記す。

### 11.2 1ソース : 1テスト

原則としてソースとテストを1対1で対応させる。プロジェクト構造上合理的な場合には、テストをソース末尾に同居させる形も許容候補とする。どちらを採用するかは言語、ビルド系、公開API、コンポーネント構成に応じて決める。

### 11.3 テスト用コンテキストとExecutable

テスト対象をテスト用コンテキストで実行可能な形にし、単体テストを独立して実行できる構造を目指す。テスト用の構成が本番コードの責務を不必要に複雑化させないことが条件となる。

### 11.4 モックを用いた単体テスト

外部依存をモック等で制御し、対象ユニットの振る舞いを独立して検証する。正常系だけでなく、境界値、失敗、エラー伝播、資源解放、状態遷移を検証する。

### 11.5 カバレッジ基準

C1--C4カバレッジを必須基準とする構想がある。ただし、C1--C4がこのプロジェクト内でどのカバレッジ定義・ツール指標を指すかは、現時点で確定していない。実装規約に採用する前に、各レベルの厳密な定義、測定ツール、例外条件、CIでの失敗条件を明文化する必要がある。意味を曖昧にしたまま数値だけを必須化しない。

-   定義が確定していなくても、最上位のレベルを最低ラインとして定義する。**[方針]**
-   最上位レベルの参照基準として、MC/DC(DO-178Cの最上位レベルで要求される基準)を候補とし、C1--C4との対応表を作る。**[提案]**
-   適用範囲を明確にする。カーネル／HAL、検証・採択経路(9.4)、ace-cc、libace_rt は必須とし、周辺ツールと互換レイヤーは別途決定する。全コードに最上位の基準を課した場合のコストを見積もる。**[提案]**

## 12. 公開開発とライセンス思想

### 12.1 公開方針

非公開の開発期間を設けず、誰でもアクセスできる公開リポジトリで開発する方針。OSS本体を秘匿して競争優位を作るのではなく、公開された実装・仕様・開発履歴を基盤とする。

### 12.2 AceGeneralPublicLicense

独自の名称として **AceGeneralPublicLicense**
を用いる構想がある。AGPLという略称は既存のGNU Affero General Public
Licenseと混同される可能性があるため、法的文書や配布時には正式名称、略称、適用条項の識別を明確にする必要がある。本書はライセンス条文そのものではなく、法的効力を持つ利用条件を代替しない。

OSI承認を前提に設計する必要はないという意向である。ライセンスの目的、著作権表示、ソース公開条件、ネットワーク経由利用、派生物、特許、商標、免責、準拠法などの具体的条項は、条文を作成・レビューする段階で確定する。

### 12.3 ソース内の表記を最小化する

ソースコードに個別の長いライセンス文を繰り返し記載することは避けたい。可能であればソース内のライセンス表記を省き、必要な場合も
`AceGeneralPublicLicense` の名称程度に抑える方向である。

一方で、著作権の帰属や利用条件を利用者が確認できなくなる構成は避ける。トップレベルにライセンス文書と著作権・貢献記録の体系を置き、各ソースとどの記録が対応するかを追跡可能にする。

### 12.4 貢献者と著作権の履歴管理

著作権・貢献範囲を単一の巨大なファイルに集約しない。トップレベルで一元的に見つけられる構造を用意しつつ、記録自体は分割し、時系列で追跡できるようにする。

設計上の要件:

-   誰が、いつ、どの範囲に貢献したかを記録する。
-   貢献者の記録と、著作権・ライセンス上の扱いを対応付ける。
-   変更履歴を後から検証できるようにする。
-   大規模な一枚ファイルを避け、コンポーネント別・期間別・変更単位等の適切な分割を検討する。
-   ファイル名、記録形式、改訂・訂正方法、個人情報の扱いを標準化する。
-   Gitの履歴だけに依存するか、別の明示的な貢献記録も併用するかは未確定。

ライセンス表記をソースから減らすことと、著作権・貢献履歴の追跡可能性を弱めることは別問題として扱う。

### 12.5 収益とOSS

収益化の中心をソースの非公開化に置かず、必要に応じてサポート、移植、認定、保守等を検討する。特定の収益モデルをこの設計書で確定するものではない。OSS本体の公開と、持続可能な開発・保守体制を両立させる。

### 12.6 依存・参照ライセンスの管理

-   ace-cc と libace_rt は自前のコードで構成し、既存コンパイラ(GCC、LLVM等)のコードを取り込まない。**[方針]**(10.1に由来)
-   gcc／clang等は、ブートストラップと基準としてのみ使う外部ツールとして扱う。通常は生成物のライセンスに影響しないと考えられるが、専門家に確認する。**[提案]**
-   Phase 0で、使用・参照する外部ツール、ライブラリ、仕様書のライセンス一覧を作成する。**[提案]**
-   互換レイヤーは別リポジトリ・別パッケージとし、ライセンスを本体から分離できるようにする。**[提案]**
-   ソース内のライセンス表記は、SPDX形式の1行識別子(独自ライセンスにはLicenseRef-接頭辞を使う形)で機械可読にする案を検討する。**[提案]**
-   AIが生成したコードに、既存OSSに酷似したコードが混入していないか、出所を確認する工程を設ける。**[提案]**
-   ライセンスに関する法的判断は、専門家のレビューを経て確定する。

## 13. ガバナンスとメンテナンス

### 13.1 Founderの役割

Founderは設計思想、全体の方向性、最終的なガバナンスを保持する一方、日々のコンポーネントメンテナー業務を自ら継続する前提にはしない。

### 13.2 コンポーネント単位の責任

各コンポーネントに責任者・メンテナーを置き、責務に応じて設計判断、レビュー、マージ、リジェクトを行えるようにする。全判断を一人に集中させない。

### 13.3 AIと人間の役割

AIは解析、テスト、レビュー支援、変更案生成、回帰検出を担えるが、責任境界と権限は明確にする。AIによる生成量を開発品質と同一視せず、検証可能な成果物と責任者を基準にする。

### 13.4 開発基盤の方向性

GitHub Organization、Pull
Request、CI、CODEOWNERS等を使い、コンポーネントごとに責任範囲を明確にする構想がある。具体的なブランチ戦略、署名要件、リリース権限、セキュリティ対応手順は未確定。

## 14. 適用領域

構想上の適用領域は単一の組込み用途に限定しない。

-   次世代の一般用途OS
-   Minimum AI RTOS
-   RTOS with Gaming Specs
-   ゲーミングや高応答性が要求されるシステム
-   ロボット
-   航空宇宙
-   組込み制御・産業用途
-   SIMDを活用する計算環境
-   個人の作業環境・開発環境
-   エンジニアが起動、観測、実験、計測、改善を楽しめる開発プラットフォーム
-   システムの内部動作を必要な範囲で可視化し、利用者が意識しなくても改善の恩恵を受けられるエンドユーザー環境

ただし、これらを同時に初期リリース対象にするわけではない。安全性認証やリアルタイム保証が必要な分野は、一般用途の機能開発とは別に、要求分析・検証・認証計画が必要となる。

## 15. 非目標・避ける設計

現時点の思想から、少なくとも次の方向は避ける。

-   複雑な構造をそのまま利用者へ露出する。
-   AIの要約だけを一次記録として扱い、rawログを失う。
-   巨大な単一ファイルにすべての記録や責務を詰め込む。
-   すべての判断・保守をFounder一人に集中させる。
-   最初から複数アーキテクチャを同時に完成させようとする。
-   AIが生成したという理由だけでコードを信頼する。
-   テストやカバレッジの定義を曖昧にしたまま品質を主張する。
-   OSS本体を非公開にすることを主要な収益化手段とする。
-   POSIX互換を将来にわたる絶対条件として固定する。
-   自動最適化を、検証・監査・ロールバックなしの自動変更と混同する。
-   互換レイヤーの都合で、カーネルの設計を複雑にする。**[提案]**
-   信頼度が高いことを理由に、検証の厳しさを下げる。**[提案]**
-   出所が確認できないコード(AI生成を含む)を、確認なしに取り込む。**[提案]**
-   エンジニア体験とエンドユーザー体験のどちらか一方を、恒常的に犠牲にする。
-   すべての変更をマイクロ秒単位で完全検証できると主張する。
-   最初の実装を、機能数や商用完成度だけで評価し、開発者が触って学べる体験を後回しにする。

## 16. 開発の段階案

以下は議論に現れた方向性と、レビューで出た組み替え案を整理した段階案であり、確定した工程表ではない。中核仮説であるACEコンポーネントを含む自己改善フィードバック・ループを、AceIS全体の実装を待たずに先に薄く検証する。**[提案]**

### Phase 0 --- 仕様・検証基盤・ライセンスの定義

-   Project-KISS / Project-ACE / AceIS / AceIS Core / A-Nexus / Abiss の責務境界を文書化する。
-   エンジニアとエンドユーザー双方の体験要件を初期要件として定義する。
-   リアルタイム経路と自己改善サンドボックスの分離方針を定義する。
-   初期PoCの対象CPUを一つ選ぶ(互換レイヤーとの関係を考慮する。5.7)。
-   ビルド・テスト・カバレッジ・生成物検証の基準を決める。C1--C4の最上位レベルの定義を含む。
-   ソースとテストの構成規約を試作で評価する。
-   ライセンスと貢献履歴の文書体系を設計する。外部ツール・ライブラリ・仕様書のライセンス一覧を作る。
-   脅威モデルの骨子(第9節)を作る。

### Phase 1 --- ace-ccのPoC

-   AIRの最小意味仕様とx86-64単一バックエンドを作り、SIMD生成を段階的に検証する。
-   Core Dump取得・AIR Mapping・GDB事後解析の最小経路を整備する。専用SIMDデバッガの完成は開始条件にしない。

-   x86_64/amd64ホスト上で動作させる。ターゲットを一つに絞る。
-   ace-ccで小さなプログラムのコンパイル、アセンブリ確認、リンク、実行またはシミュレーションを通す。
-   gcc／clangは、ブートストラップと出力の差分テストの基準としてのみ使う。
-   libace_rtの最小部分を用意する。
-   テストを並列実行し、全体時間の目標を計測する。
-   ターゲット切替の構造を検証する。

### Phase 2 --- 実行・観測基盤と、薄いACEループ

-   rawログのフォーマット、保存、検索を定義する。
-   再現可能なテストと実行結果の記録を作る。
-   変更・ビルド・テスト・測定の対応関係を追跡する。
-   AI解析を一次記録から分離して接続する。
-   **ace-ccのPoC上で、AIが変更案を出し、テストと計測で検証し、適用判断と再観測を行う最小のループを先に通す。** OSは不要で、中核仮説の成否を早く確認できる。
-   採択経路の最小版(関門と署名)を試作する。

### Phase 3 --- AceISの最小実行基盤

-   カーネル／HALとユーザーランドRuntimeの境界を定義する。
-   初期API、実行モデル、メモリ・スケジューリング要件を決める。
-   POSIX互換をどこまで初期入口に用いるかを決める。
-   対象環境で起動・実行・テストできる最小構成を作る。

### Phase 4 --- ACEフィードバック・ループの本体統合

-   解析、生成、検証、適用の責務を分ける。
-   AIの提案に根拠・テスト結果・差分を結び付ける。
-   リスクに応じた自動化権限を定義する。
-   適用後の再観測とロールバックを検証する。
-   各個体での検出・隔離・解析・対策・レポート共有、個体の信頼度、更新経路(最小差分とローカルビルド)を実装し、脅威モデルを検証する(第9節)。

### Phase 5 --- 互換レイヤー(別パッケージ)

-   静的リンクLinux ELF、動的リンクLinux ELF、Windows PEの順に段階的に対応する(5.7)。
-   実行モード(隔離／性能)を実装する(5.8)。
-   削除条件を定義する。

### Phase 6 --- 拡張

-   ターゲットCPUを追加する。
-   SIMD Native、移植を拡張する。
-   RTOS、ゲーミング、ロボット等の要件に応じて専門機能を追加する。
-   リアルタイム性や安全性が必要な領域では、個別の測定・認証計画を設ける。

## 17. 未決事項一覧

次の項目は、構想の一貫性を保つためにも、今後明示的な決定が必要である。

1.  **Project-KISS / Project-ACE / AceISとACEコンポーネントの成果物境界:**
    Project-KISSは各コンポーネントとAceISを開発する最上位プロジェクト、Project-ACEはAceISを作るサブプロジェクト、AceISはACE／PAUL／GENE／PETERなどを包含する統合ISとする。文書では「Project-ACE」「ACEコンポーネント」「AceIS Core」「AceIS」を明示的に区別する。AceIS Coreは統合システムの全体制御・判断、ACEコンポーネントは推論・検証・改善候補の導出を担う方向で整理するが、詳細な責務契約、リポジトリ、成果物の単位は今後決定する。
2.  **カーネル構成:**
    Abiss / A-Nexus / AceIS Coreという論理的責務分担は本版で暫定採用する。一方、マイクロカーネル、モノリシック、ハイブリッド等の実装構造や、各機能の特権レベル・プロセス配置は未確定。
3.  **初期ターゲット:** 最初に完成させるCPUと実行環境。amd64であれば互換レイヤーの検証が容易になり、他のCPUであればバイナリ変換が最初から必要になる(5.7)。
4.  **コンパイラ戦略:**
    ace-ccの方針は第10.1節のとおり。残る課題は、ace-ccの自己ホスト化におけるブートストラップの手順と検証方法、最初のPoCで対象とする言語機能の範囲。
5.  **API/ABI:** POSIX互換の範囲、独自API/ABI、互換性・バージョニング。互換レイヤーの範囲(ELF静的／動的、PE)、本体との依存方向の規則、削除条件。
6.  **AI実行配置:**
    ローカルモデル、外部モデル、役割ごとのモデル、通信プロトコル。
7.  **自動適用権限:**
    どの変更を自動適用可能とし、何を人間またはメンテナー承認必須とするか。個体ローカルの緩和と、全体へ波及するパッチの線引き(9.4)。
8.  **ログ仕様:**
    イベント形式、レコード幅、保持期間、容量目標、機密データの扱い。

## 18. 設計判断の記録方法

### 18.1 記録方法

今後の意思決定では、確定事項、採用理由、却下した案、未解決のリスクを区別して記録する。過去の議論を、後から都合よく確定仕様に読み替えない。

各設計判断には少なくとも次を記録する。

-   IDとタイトル
-   状態（提案／検討中／決定／廃止）
-   日付
-   背景と問題
-   決定内容
-   理由と制約
-   検討した代替案
-   影響するコンポーネント
-   検証方法と見直し条件

設計思想の文書と、実装仕様、ADR（Architecture Decision
Record）、API仕様、テスト規約、ライセンス文書は、役割を分けて管理する。本書は全体像を把握する入口であり、個々の規範文書の代替ではない。

### 18.2 ADR候補

18.1の形式で記録する前の候補一覧。状態はいずれも「提案」であり、決定済みではない。「出所」は、設計者が明示した方針か、レビューで出た提案かを示す。

| 候補 | 内容 | 出所 |
|------|------|------|
| ADR-A | ace-ccを独自開発し、既存コンパイラ・LLVMを生成物に取り込まない。gcc/clangはace-cc完成まで | 方針 |
| ADR-B | 互換レイヤーは本体から分離し、ユーザーランドに閉じ、最終的に削除する | 方針(依存方向と削除条件は提案) |
| ADR-C | サンドボックスは実効速度が担保できる場合のみ。直通経路はモードで扱う | 方針(既定値は提案) |
| ADR-D | assume breach。検出・隔離・解析・対策・共有をACEコンポーネントとAceISの連携で回す | 方針 |
| ADR-E | 更新は最小差分を取得し、AceIS側でローカルにビルド・検証して取り込む（完成済みイメージのOTA配布を前提としない） | 方針 |
| ADR-F | 貢献度・信用度は個体に付与し、人間には非公開とする | 方針(監査ログは提案) |
| ADR-G | パッチ採択経路(関門、閾値署名、段階展開、採択経路の保護) | 提案 |
| ADR-H | カバレッジは最上位レベルを最低ラインとする(MC/DCを候補) | 方針(MC/DCは提案) |

## 19. 最終的な方向性

Project-KISSは思想と自由の原則を軸に、ACE／PAUL／GENE／PETERなどの各コンポーネントとAceISを開発する。Project-ACEはProject-KISSのサブプロジェクトとしてAceISを設計・実装・検証し、AceISは各コンポーネントを包含する統合ISとして利用者に提供される。

その中心にあるのは、AIを単に既存ソフトウェアへ追加することではない。システム自身が自らの動作を観測し、根拠を保持し、変更を検証し、必要に応じて生成・最適化できる構造を作ることである。

ただし、自律性は無制限の権限を意味しない。検証可能性、記録の完全性、責任境界、利用者の自由を維持して初めて、自己改善は信頼できるシステム機能となる。

**Project-KISSは全体構想と原則を、Project-ACEはAceISの構築を、ACE／PAUL／GENE／PETERは機能責務を、AceISは統合された利用体験を担う。**

AceISでは、エンジニアが作る楽しさと、エンドユーザーが使う楽しさを両立する。自律的な自己改善はその両者をつなぐ仕組みであり、性能向上だけでなく、理解・実験・適応・自由を支えることを目指す。
